# AI Tool Management Generated ID And Draft Creation Design

## Summary

Adjust AI tool management creation so operators no longer edit `toolchain_id` directly. Creating a toolchain starts by asking for a display name, then immediately creates an in-memory draft row in the left list and opens the detail editor for that draft. The internal `toolchain_id` is generated by the system using a normalized name prefix plus a random suffix so exported/imported packages are less likely to collide with existing local toolchains.

## Problem

The current AI tool management UI exposes both `工具链标识` and `显示名称` as editable required fields. This makes the form feel redundant to users, but the fields are not actually equivalent:

- `display_name` is user-facing text.
- `toolchain_id` is the stable internal identity used for AI bindings, execution history references, and config package import/export conflict handling.

Letting operators edit `toolchain_id` directly is error-prone. It also makes `新建` feel incomplete because clicking it only clears the right-side editor; it does not create a visible draft item in the left list.

## Goals

- `新建` should first ask for a display name.
- Confirming `新建` should immediately create a visible selected draft item in the left list.
- `toolchain_id` should be auto-generated by the system and no longer be user-editable in the AI tool management UI.
- Generated `toolchain_id` values should include a random suffix to reduce import/export package collision risk.
- Existing persisted toolchains keep their current IDs; this is a UI workflow change, not a data migration.
- Keep the change localized to AI tool management UI, AI toolchain ID generation support, and related tests.

## Non-Goals

- Changing hardware management code.
- Reworking AI request/response protocol or runtime execution behavior.
- Changing config import/export conflict rules beyond reducing future `toolchain_id` collisions via generated IDs.
- Migrating existing toolchain rows to new IDs.
- Removing `toolchain_id` from persistence or package metadata.

## Existing Context

Current behavior:

- `ui/modules/ai_tool_management.py` exposes editable `工具链标识` and `显示名称`.
- `新建` clears the editor and marks `_is_new_draft = True`, but it does not insert a draft row into the left list.
- `app/service/ai_service.py` requires `toolchain_id` on save and enforces uniqueness.
- The left list currently renders `display_name (version) - toolchain_id`, which is useful because display names are not guaranteed unique.

This means the system already treats `toolchain_id` as a distinct stable identifier, but the UI still asks users to manage it manually.

## Approaches Considered

### Recommended: service-generated internal ID, UI draft row, read-only ID display

- `新建` asks only for `display_name`.
- The service provides a helper to generate a unique `toolchain_id`.
- The module creates an in-memory draft row immediately after name confirmation.
- The detail editor shows the generated internal ID as read-only information.

Pros:

- Preserves a stable internal identity without making users invent one.
- Keeps import/export semantics explicit because `toolchain_id` still exists and remains stable.
- Minimizes scope by keeping changes inside AI tool management and AI service.

Cons:

- Requires new draft-row behavior in the list.
- Requires UI/test updates because create no longer starts from a blank editor.

### Alternative: UI-generated internal ID without service support

- The module generates the ID locally and passes it into `save_toolchain`.

Pros:

- Slightly smaller immediate code change.

Cons:

- Pushes an identity-generation rule into one UI instead of the AI domain service.
- Makes future reuse harder for other AI toolchain entry points.

### Alternative: hide `toolchain_id` entirely from the UI

- Users never see the internal ID.

Pros:

- Simplest operator-facing form.

Cons:

- Makes debugging import/export and conflict handling harder.
- Removes a useful diagnostic surface when duplicate display names exist.

## Product Decisions

### New Flow

- Clicking `新建` still respects the current unsaved-change prompt flow.
- If the user proceeds, show a text input dialog asking for `显示名称`.
- If the dialog is cancelled, do not create a new draft. The module remains in the state produced by any prior unsaved-change decision:
  - if the user cancelled at the unsaved-change prompt, nothing changes
  - if the user chose save or discard at the unsaved-change prompt, that save/discard result stands, but no new draft is created
- If the confirmed display name trims to empty, show a validation warning and do not create a draft.
- If confirmed with a non-empty display name, create an in-memory draft toolchain row and select it immediately in the left list.

### Draft List Behavior

- The new in-memory draft row appears in the left list immediately after `新建` confirmation.
- The draft row is inserted at the top of the left list for visibility.
- The draft row is selected and the detail pane is shown.
- The draft row is not persisted until the user clicks `保存`.
- The draft row should be visibly distinguishable as unsaved, for example by appending ` [未保存]`.
- The draft row label updates live when the draft's `display_name` or `version` changes in the editor.
- If the edited draft display name becomes empty in the editor, the left list falls back to a placeholder such as `未命名工具链`, while keeping the generated internal ID visible.
- The existing `删除` button remains disabled for an unsaved draft; draft discard continues to happen through the unsaved-change flow rather than a dedicated delete path.
- Saving the draft converts the draft row into a normal persisted row and removes the unsaved marker.
- Choosing `放弃更改` while leaving, switching selection, or starting another `新建` removes the current draft row entirely.
- Choosing `保存并继续` while a draft is active persists it first, then continues the pending action.
- Choosing `取消` while a draft is active keeps the draft row and editor unchanged.

### Internal ID Generation

- Add AI-service-owned toolchain ID generation support, for example `AiService.generate_toolchain_id(display_name)`.
- Generated IDs use:

```text
<sanitized_name_prefix>_<random_hex_8>
```

- `sanitized_name_prefix` rules:
  - trim whitespace
  - lowercase
  - normalize with Python standard-library `unicodedata.normalize("NFKD", value)`, then `encode("ascii", "ignore").decode("ascii")`
  - replace each run of characters outside `[a-z0-9]` with `_`
  - trim leading/trailing `_`
  - cap the prefix at 24 characters
  - if empty after normalization, use `toolchain`
- `random_hex_8` comes from secure random bytes or UUID hex.
- Final generated IDs therefore have maximum length `24 + 1 + 8 = 33` characters.
- Generated IDs must still be checked against existing persisted toolchains; regenerate if a collision occurs.
- The generated ID is stable for the life of that toolchain after creation.
- When a draft is first created, also capture and store an immutable `generated_id_prefix` alongside the draft payload.
- `generated_id_prefix` is derived once from the display name used at draft creation time and does not change after later display-name edits.
- Any later regeneration for that draft must reuse the same stored `generated_id_prefix` and only replace the random suffix.

Examples:

```text
motor_ai_a7f3c9d2
toolchain_3e1b54aa
```

### UI Treatment Of Internal ID

- The editable `工具链标识` field is removed from the AI tool management form.
- Replace it with a read-only internal ID display labeled `内部标识` or equivalent.
- New drafts show the generated ID immediately.
- Existing saved toolchains show their existing persisted ID in the same read-only field.
- The UI no longer allows renaming a toolchain by changing `toolchain_id`.

### Save Behavior

- New draft saves use the pre-generated `toolchain_id`, but re-check availability immediately before persistence.
- If a new draft's generated `toolchain_id` has become occupied before save, the module requests a freshly generated ID from `AiService`, updates the draft's read-only internal-ID display and left-list label, and then saves using the regenerated ID.
- Extend the AI-service create contract for generated-ID drafts only:
  - create requests may include `generated_id_prefix`
  - if `save_toolchain()` is called with `original_toolchain_id is None` and `generated_id_prefix` is present, a create-time `toolchain_id` uniqueness conflict is treated as retriable generated-ID collision
  - in that narrow case, `AiService` regenerates a fresh ID from the same stored prefix, retries the insert once, and returns the actual saved ID
  - all other save failures continue to surface as normal errors without retry
- Existing toolchain edits preserve the existing `toolchain_id`.
- Display-name edits do not change `toolchain_id`.
- Service-level uniqueness and package-dir validation remain in place.

### Left List Rendering

- Keep the current list label structure based on `display_name`, `version`, and `toolchain_id`, because display names may repeat.
- Draft rows append an unsaved marker.

## Design

### `AiService`

Extend `app/service/ai_service.py` with an explicit helper for new internal IDs.

Responsibilities:

- Normalize a display name into a readable prefix.
- Append an 8-character random hex suffix.
- Retry if the generated ID already exists in `AiToolchainTable`.
- Support regeneration from an already chosen immutable prefix for generated-ID drafts.

Compatibility decision:

- `save_toolchain()` keeps accepting explicit `toolchain_id` values so config import/export and tests can continue supplying source package IDs when needed.
- Generated-ID retry behavior is limited to new UI drafts that explicitly pass `generated_id_prefix`.
- The UI is the only surface changing from editable IDs to generated IDs.

### `AiToolManagementModule`

Update `ui/modules/ai_tool_management.py` so:

- `新建` uses a name-entry dialog first.
- Confirmed creation builds a normalized draft payload with:
  - generated `toolchain_id`
  - immutable `generated_id_prefix`
  - confirmed `display_name`
  - existing default values for timeout, execution mode, enabled, etc.
- The module tracks one active draft row and injects it into the left list alongside persisted rows.
- Selecting the draft loads the draft payload instead of expecting a persisted row from `_toolchain_rows`.
- The editor replaces editable `ed_toolchain_id` input with a read-only internal-ID display widget.
- Existing unsaved-change flows remain intact for switch/new/leave, with one explicit extension: an active unsaved draft counts as pending unsaved work even if the operator has not edited any fields after the initial draft was created.
- The existing `删除` action remains unavailable for unsaved drafts, so draft removal continues to happen only through the switch/new/leave discard path.

### Tests

Update focused UI/service tests to cover:

- generated IDs contain a readable prefix plus random suffix
- generated IDs are ASCII-only and do not exceed the agreed maximum length of 33 characters
- generated IDs regenerate on collision
- regenerated draft IDs reuse the original immutable prefix and only replace the random suffix
- `新建` asks for display name first
- cancelling the name dialog leaves the module unchanged
- cancelling the name dialog after a prior save/discard decision creates no new draft
- confirming a name creates a visible selected draft row in the left list
- the draft row is marked unsaved
- the draft row appears at the top of the list
- editing draft display name updates the left-list label live
- the draft editor is prefilled with display name and read-only generated internal ID
- an active unsaved draft still triggers the existing save/discard/cancel flow on switch/new/leave
- choosing discard from that flow removes the draft row
- saving a new draft persists the generated ID
- saving a new draft that hits a pre-save collision regenerates a fresh ID from the same prefix
- saving a new draft that hits a create-time uniqueness collision retries once with the same prefix and a new suffix
- existing toolchain rows still load and show their internal ID read-only
- display-name duplicates remain allowed

Run:

```powershell
pytest tests/test_ai_service.py tests/test_ai_tool_management_module.py -q
```

## Compatibility / Migration

- Backward compatibility: partial.
- Protected surfaces:
  - persisted `toolchain_id` values for existing rows
  - AI binding references
  - config import/export metadata semantics
  - AI runtime execution behavior
  - hardware management code
- Allowed breakage:
  - AI tool management UI no longer allows editing `toolchain_id`
  - create flow now requires entering display name before the draft appears
- Migration strategy: none. Existing rows keep current IDs and simply become read-only in the UI.

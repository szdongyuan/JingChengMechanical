# 批量导出进度重入导致闪退的修复设计

日期：2026-09-16。用户已确认方案 A（局部修复进度刷新）；本文已通过独立 spec-document-reviewer 审查，用户于 2026-09-17 确认规格并授权开始实施。

## 问题与证据

用户报告同一批 400 多条记录仅导出 Excel 时闪退，单条正常；全选导出项时 ZIP 及其中 Excel 正常。退出前窗口停留在“正在读取 AI 导出数据…”。该文字只能说明最后显示的阶段，不能认定崩溃发生在 AI 读取代码内。

本地使用真实 `DataManagementModule`、`_ExportWorker`、模态 `QProgressDialog` 和 `write_run_data_export`，为 450 条合成记录生成独立 XLSX，复现 Windows `stack overflow`。主线程堆栈反复进入 `update_progress` 中的 `QApplication.processEvents()`；工作线程仍在逐条发送准备进度。仅在诊断进程屏蔽该处显式事件处理后，工作线程正常结束，生成的工作簿有 451 行（表头加 450 条记录）。诊断没有修改正式源码。

本地证据：`outputs/excel-export-diagnosis-20260916/real-export-stack.log` 与 `qt-reentrancy-control.json`。这些文件是辅助证据，回归测试不得依赖其存在。用户电脑没有提供崩溃堆栈；这里修复的是已复现且与现场特征吻合的代码缺陷。

AI 全量结果解析存在独立性能成本，但不能解释同一批数据的两种导出结果差异。附件 I/O 会改变进度发送时序，因而全选导出没有闪退不能证明该路径不存在重入风险。

## 目标和范围

- 消除进度回调主动运行事件循环所产生的无界递归，恢复大批量独立 XLSX 导出。
- 保留后台导出及主线程进度更新；保证成功、失败、取消后的窗口收尾不被残留进度覆盖。
- 通过真实 Qt 窗口及真实文件输出验证，覆盖单条、450 条、1000 条和同批全选导出。
- 改动限于 `ui/modules/data_management.py` 的导出进度/收尾边界及相应测试。

不在本次范围：AI 导出读取优化、数据库索引或迁移、附件打包提速、导出格式调整、通用任务框架、应用退出生命周期重构、发布安装包。用户提出的未来加速需求另行设计。

## 方案选择

选择 A：移除进度回调的显式 `processEvents()`，沿用现有 queued signal 与 Qt 事件循环，并在终态后拒绝旧进度。该方案已有最小对照实验支持，改动范围小。

备选 B：定时合并进度、只绘制最新状态。它能减少绘制次数，但引入定时器、缓存及额外生命周期管理；本次不采用。不得通过后台 sleep、降低导出速度或更改 Python 递归上限掩盖故障。

## 交互与实现边界

### 正常进度

`_ExportWorker` 继续执行导出并通过 `progress_changed` 发送数据，GUI 继续使用 `QueuedConnection`。导出回调仅更新当前进度窗口，不显式调用 `QApplication.processEvents()`，不调用 `exec()`，不等待工作线程，不开启额外事件循环。

保留现有从不确定进度转为确定进度的规则、单调不回退的数值、阶段说明及窗口模态设置。Qt 控件内部可能处理事件，因此验收要求是应用不再造成随消息数量增长的递归，不要求 Qt 的调用深度绝对为 1。

本次仅针对进度回调中的重复事件处理；启动导出前的界面显示处理以及其他功能中的事件处理不作顺带修改。

### 终态与残留消息

每次导出以该次进度窗口实例为身份。处理进度前确认它仍是 `self._export_progress`，且本次操作未进入终态；旧导出的回调不能更新后续导出的窗口或状态。

`_finish_export` 继续先撤销当前进度窗口身份，再关闭窗口和恢复操作控件。进度回调内调用可能处理事件的控件方法后，若继续更新界面，应再次检查本次窗口仍有效，防止嵌套处理的终态通知返回后继续写旧窗口。窗口关闭后的队列残留应直接忽略。

成功、失败和取消保留原有提示及结果语义。工作线程已返回成功时，随后收到取消请求不能把成功改成取消。取消仍通过现有检查点协作执行；本次不承诺缩短 AI 读取阶段的取消等待。窗口关闭不等于线程已经停止，现有 `finished` 信号清理责任继续保留。

导出按钮随当前操作状态恢复，用户能在前一次正常收尾后再次导出。此次不新增运行中关闭整个应用的行为。

### 文件正确性

沿用现有准备、写临时文件、校验、原子替换顺序。失败和取消保留原目标，清理本次临时文件。Excel 行、字段类型、序号、时间转换、AI 取值、ZIP 清单和附件选择规则均不改变。

## 测试与验收

1. **修复前可失败的真实 GUI 回归**：在独立 Python 子进程中启动真实 `QApplication`、`DataManagementModule`、进度窗口与 `_ExportWorker`；使用真实导出内核及 450 条合成记录，不替换进度窗口为 stub。通过同步事件构造准备进度快速排队的时序，避免靠固定 sleep 作为唯一复现条件。父进程检查超时、退出码、子进程诊断及输出内容；Windows 栈溢出不能拖垮整套 pytest 或弹出系统故障交互框。
2. **规模与内容**：修复后 1、450、1000 条独立 XLSX 均正常收尾，导出数与唯一记录标识吻合，表头加数据行数为 N+1，正常退出，无栈溢出/递归异常。450 与 1000 条用于验证规模增长不引起进度回调栈深度随记录数增长；不使用硬编码耗时作为性能承诺。
3. **相同记录的组合导出**：使用同一批合成运行记录及小型有效 WAV、电流数据、选定数据库副本，验证全选输出 ZIP 及内部 XLSX 可读，实际包含选中的附件，核对共同汇总字段与独立 XLSX 一致。音频相对路径列在两种选择下按原规则允许不同。
4. **终态保护**：成功、失败、取消后显式投递残留进度，确认不改变终态、不触碰失效窗口、不影响后续导出；覆盖旧回调遇到新的窗口实例。覆盖终态在控件事件处理中被处理、外层回调随后恢复的情况。
5. **取消和失败**：在现有可取消阶段触发真实取消，确认工作线程结束、控件恢复、原目标保留、临时文件清理；注入写入失败并检查同样的收尾要求。保留成功结果优先于迟到取消的既有测试。
6. **现有回归**：运行 `tests/test_data_management_module.py`、`tests/test_run_record_export_dialog.py`、`tests/run_record_export/` 和 `tests/run_persistence/test_ai_export_reader.py` 中相关检查；新增真实 GUI 子进程测试可独立成文件，以避免崩溃用例污染普通 UI 测试。

测试在临时目录使用合成数据，不修改实际业务数据库，不依赖现场文件。允许模拟选择对话框和成功/失败消息框来避免交互阻塞，但不得绕过真实进度更新路径。

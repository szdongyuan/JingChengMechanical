# 所选配置 PLC 启动信号归位设计

## 背景

普通测试 PLC 当前只在启动位从 `0` 变为 `1` 时触发测试。`PlcService`
第一次读取启动位时只记录基线，不触发；检测到上升沿后才会把启动位自动写回
`0`。如果软件在收到或处理启动信号期间退出、失效，PLC 启动位可能一直保持
`1`。软件再次启动后会把这个 `1` 当作初始基线，因此既不显示收到新信号，也
不会开始录音。

现场暂时继续使用单启动位协议和上升沿检测。本改动提供一个恢复措施：在准备
使用某个测试配置时，先把该配置绑定 PLC 的启动位写回 `0`，为下一次
`0 -> 1` 上升沿建立可靠基线。

## 术语

- “归位”或“刷新启动信号”：使用该 PLC 已配置的
  `start_signal_offset`，向启动位写入布尔值 `False`。
- “启动所选配置”：软件启动时从本地设置恢复并仍然有效的所选配置。
- “新勾选配置”：一次用户选择变化中，相对变化前新增的配置；取消勾选不属于
  新勾选。

## 目标

1. 软件启动后，对启动所选配置绑定的每个普通测试 PLC 请求一次启动位归位。
2. 用户新勾选配置时，先登记并投递一次其绑定 PLC 的启动位归位请求，再更新
   配置选择。
3. 多个配置绑定同一个 PLC 时，同一批请求只归位一次。
4. PLC 服务尚未创建或尚未连接时保留归位请求；服务可用后执行归位，成功后以
   `False` 作为启动位检测基线。
5. 归位成功或失败均写入现有应用日志，失败不能导致界面崩溃。
6. 每次软件启动恢复和每次新勾选各产生一批一次性请求；请求成功后，普通断线
   重连或服务重建不得重复归位。

## 非目标

- 不把初次读取到的高电平当作启动请求。
- 不改变现有 `0 -> 1` 上升沿触发规则。
- 不引入新的 PLC 确认位、请求序号或数据库字段。
- 不保证软件或 PLC 故障期间的启动请求“恰好一次”处理。
- 不归位未被所选配置绑定的普通 PLC，也不影响工艺 PLC。
- 不在取消勾选配置时归位 PLC。

## 方案比较

### 方案 A：带挂起状态的显式归位请求（采用）

配置选择层只识别启动恢复和新增勾选时机，服务容器把配置 ID 映射为 PLC ID
并去重、持久保存当前进程中的挂起 PLC ID，再通过总线向对应 `PlcService`
发出归位请求。每个 `PlcService` 在自己的线程中写 PLC；尚未连接时继续保留
请求，写入成功回执后才由服务容器移除。

优点是范围精确、界面不被 PLC 网络操作阻塞，并且不改变轮询触发规则。

### 方案 B：每个 PLC 服务启动时无条件归位

实现简单，但会修改未被当前配置使用的 PLC，并可能清除其他工位的有效信号，
不符合“以所选配置为准”的范围要求。

### 方案 C：首次读取高电平时直接启动

可以消费遗留高电平，但无法区分旧信号和新信号，软件重启后可能重复录音。该
方案改变了用户确认保留的上升沿语义，因此不采用。

## 设计

### 归位请求协调与配置到 PLC 的映射

`ServiceContainer` 持有仅存在于当前软件进程的
`pending_plc_start_signal_reset_ids` 集合，并提供一个集中入口接收配置 ID
序列：

1. 逐个通过现有 `ConfigService.load_config()` 加载配置。
2. 只接受非布尔整数类型的 `plc_id`。
3. 按首次出现顺序去重 PLC ID。
4. 把每个有效 PLC ID 加入挂起集合；同一批和当前已挂起的重复 ID 不重复
   投递。
5. 如果对应 PLC 服务已经注册，则发出一次启动信号归位请求；服务缺席时只
   保留挂起状态。
6. 收到 PLC 服务的成功回执后，从挂起集合移除该 PLC ID；失败回执不移除。
7. 配置不存在、加载失败或未绑定 PLC 时跳过该项并记录日志，不影响其他项。

该入口只负责路由，不直接进行 Snap7 网络写入。

### 软件启动恢复

`WorkOrderModule` 仍先按现有规则恢复并校验保存的配置选择。恢复完成后，将
最终有效的配置 ID 作为一批启动归位请求登记到 `ServiceContainer`。此时 PLC
设置页和 PLC 服务可能还没有创建，所以请求必须保存在服务容器，而不是依赖
当时是否存在总线接收者。

`PlcSettingsModule.start_connect()` 创建并注册普通 PLC 服务后，要求服务容器
重新投递该 PLC ID 的挂起请求。只有挂起集合包含该 ID 时才投递；此前已成功
归位且已移除的 ID，不会因为手动重连、断线重连或服务重建再次归位。

这同时覆盖：

- 开机自动连接的所选 PLC；
- 软件启动时未自动连接、之后由用户手动连接的所选 PLC。

未被所选配置绑定的 PLC 服务不设置首次归位标记。

### 新勾选配置

`WorkOrderModule._on_config_selection_changed()` 在修改控制器选择前，计算
`new_selected - previous_selected`，先把新增配置交给集中路由入口，再调用
现有 `set_selection()`。已有配置和取消勾选配置不产生归位请求。

归位网络写入通过 PLC 工作线程异步执行，不阻塞配置界面。选择和持久化仍沿用
现有流程；归位失败通过日志暴露，不回滚用户选择。这里的“先”保证软件先登记
并投递归位请求、再更新选择，不把界面改成等待 PLC 网络回执的同步流程。

本恢复措施仍受用户确认的单启动位/上升沿原则限制：如果 PLC 恰好在异步归位
完成前产生一个全新的启动脉冲，软件不保证保存该并发脉冲。目标是清除软件
失效遗留的高电平，使后续正常操作重新具有 `0 -> 1` 上升沿，而不是实现可靠
消息队列。

### PLC 服务归位状态

`PlcService` 新增线程安全的 Qt 槽和内部挂起标记：

1. 收到属于自身 PLC ID 的请求时把挂起标记设为真。
2. 未连接时不写入，保留挂起标记。
3. 连接成功后，如果存在挂起请求，向 `start_signal_offset` 写入 `False`。
4. 写入成功后把 `_last_value` 设为 `False` 并清除挂起标记。
5. 写入成功后通过总线回传 PLC ID 和成功状态；服务容器据此清除全局挂起 ID。
6. 写入失败时保留服务内和服务容器内的挂起标记、回传失败、记录错误并进入
   现有重连流程；下一次连接后重试。
7. 不属于自身 PLC ID 的总线请求不执行写入。

正常检测到上升沿后的现有自动归位逻辑保持不变。

如果 PLC 服务对象在成功前被销毁，服务容器中的挂起 ID 仍然存在；新服务注册
后会重新投递。如果归位已经成功并收到回执，随后重建服务不会再次归位。

## 错误处理与日志

- 缺少或无效的 `start_signal_offset`：记录该 PLC 无法归位，保留挂起请求。
- Snap7 写入异常：记录异常并断开当前客户端，交给现有重连定时器恢复。
- 配置加载失败或未绑定 PLC：记录跳过原因，不向任意 PLC 发送请求。
- 成功写入：记录 `PLC <id> 启动信号已归位`，便于现场确认恢复动作。

## 测试

至少覆盖：

1. `PlcService` 对匹配 PLC 的已连接归位请求写入 `False`、清除挂起状态并把
   `_last_value` 设为 `False`。
2. 未连接时请求保持挂起，连接后完成写入。
3. 其他 PLC ID 的请求不会写入。
4. 写入失败保留请求并进入重连状态。
5. 配置到 PLC 的映射会去重，跳过未绑定、无效和加载失败的配置。
6. 软件启动时 PLC 服务缺席，请求仍保存在协调器中，服务注册后才投递。
7. 成功归位后的断开重连或服务重建不会重复归位。
8. 新勾选配置先登记新增配置的归位请求，再更新选择；取消勾选和保持选择不
   归位。
9. 归位尚未成功时，全局请求不会被清除；写入失败和服务销毁后仍可重试。
10. 现有首次高电平不触发、正常上升沿触发及触发后自动归位测试继续通过。

## Compatibility / Migration

- Backward compatibility: required
- Protected surfaces: [普通 PLC 字段偏移格式、配置与 PLC 绑定、上升沿触发语义、正常触发后的自动归位、工艺 PLC、数据库结构]
- Allowed breakage: [软件启动所选配置或新勾选配置后，对其绑定 PLC 的启动位会主动写入 `0`]
- Migration strategy: none

本改动不需要数据库迁移，也不要求旧 PLC 增加字段。普通 PLC 必须具有可写且
有效的 `start_signal_offset` 才能完成归位。
